# ADR-0004: Идемпотентность операций

## Статус
Принято

## Контекст
Повторный запрос после тайм-аута не должен приводить к дублированию операции. Например, если клиент дважды просит «переведи маме 10 тысяч», деньги должны списаться один раз.

## Рассмотренные альтернативы

### Вариант A: Идемпотентность на уровне AI (в памяти)
Ключ идемпотентности хранится в сессии AI.

**Плюсы:** Простая реализация.
**Минусы:** Пропадает при перезапуске сервиса, не защищает от повторных запросов из разных сессий.

### Вариант B: Идемпотентность на уровне Core Banking API — ВЫБРАН
Каждая операция имеет `idempotency_key = hash(client_id + action_type + параметры + окно_времени)`. Core Banking проверяет ключ перед исполнением.

**Плюсы:** Защита на уровне источника истины, работает через перезапуски, межсессиевый.
**Минусы:** Требует поддержки идемпотентности в Core Banking API.

### Вариант C: Двойная проверка (AI + Core)
Идемпотентность проверяется и на уровне AI (кэш), и на уровне Core Banking.

**Плюсы:** Максимальная надёжность.
**Минусы:** Сложность поддержки двух уровней.

## Решение
Принят **Вариант B** — идемпотентность на уровне Core Banking API:
- Ключ идемпотентности генерируется из параметров операции и окна времени (24 часа)
- При повторном запросе с тем же ключом возвращается результат первой операции
- Изменение суммы или реквизитов = новый ключ = nova операция с новым подтверждением клиента

## Последствия
- Core Banking API должен поддерживать идемпотентность
- Необходимо согласовать формат ключа и окно действия с командой Core Banking
- Клиент должен быть уведомлён, если операция уже executеd по тому же ключу
